# Skill Vetter 命名与评价标准设计

## 一、命名解析

### Vetter 的含义

**Vetter** 源自动词 **vet**，意为：
- **审查、检查**（to examine carefully）
- **评估、验证**（to evaluate）
- **把关、筛选**（to screen）

**常见用法**：
- "vet a candidate" = 审查候选人背景
- "vet a document" = 仔细审核文件
- "security vetting" = 安全审查

**类似词汇**：
- Code Reviewer（代码审查者）
- Fact-checker（事实核查员）
- Gatekeeper（把关人）

### Skill Vetter 的寓意

> **为 Skill 做审查的人** —— 不是推荐，不是背书，而是独立、客观、严格的审查。

这个名字传递的信号：
- ✅ 我们是**第三方**，不是利益相关方
- ✅ 我们**严格把关**，不轻易放行
- ✅ 我们**审查细节**，不只看表面

### 命名对比

| 名字 | 问题 | 评价 |
|------|------|------|
| Skill Rating | 像评分网站，可能有刷分 | 太轻 |
| Skill Guard | 像安全工具，范围太窄 | 太窄 |
| Skill Check | 太普通，没有专业感 | 太平 |
| **Skill Vetter** | 专业、独立、严格 | ✅ 刚好 |

## 二、评价标准设计的核心挑战

你问的核心问题：**如何设计一套确实公允、有效、科学的 Skill 评价标准？**

这是整个项目的灵魂。让我系统性地拆解：

### 2.1 评价标准的"不可能三角"

```
        公允性
         /\
        /  \
       /    \
      /  ?   \
     /________\
  可操作性    科学性
```

- **公允性**：不被操纵，不受利益影响
- **科学性**：有理论依据，可验证
- **可操作性**：能自动化采集，成本低

**现实**：三者难以兼得，需要权衡。

---

### 2.2 现有评价体系的缺陷

| 体系 | 指标 | 缺陷 |
|------|------|------|
| npm 下载量 | weekly downloads | 可被 CI/CD、机器人刷量 |
| GitHub Stars | 点赞数 | 可被营销、活动冲量 |
| 用户评分 | 1-5 星 | 水军、情绪化、幸存者偏差 |
| 安全扫描 | CVE 漏洞 | 只关注安全，忽略质量 |

**共同问题**：
1. **单一指标** —— 容易被针对性操纵
2. **滞后性** —— 反映过去，不预测未来
3. **黑盒化** —— 用户不知道分数怎么来的

---

### 2.3 我们的设计原则

#### 原则 1：多维度 + 权重可调

不依赖单一指标，而是**多维度综合评估**。

```
总分 = Σ(维度得分 × 权重)
```

**权重设计哲学**：
- **来源可信度 (20%)** —— 谁做的比做什么更重要
- **透明度 (20%)** —— 敢不敢公开信息是信心指标
- **可持续性 (15%)** —— 会不会突然跑路
- **技术价值 (15%)** —— 是真技术还是套壳
- **安全审计 (15%)** —— 底线要求
- **社区反馈 (10%)** —— 真实用户声音
- **使用指标 (5%)** —— 仅作参考，权重最低

#### 原则 2：红旗一票否决

某些红线问题，**直接降低评级**，不管其他维度得分多高。

| 红旗 | 扣分 | 说明 |
|------|------|------|
| 官网无团队信息 | -10 | 不敢公开身份，可信度存疑 |
| 已知安全漏洞 | -20 | 底线问题 |
| 过度权限要求 | -15 | 可能窃取数据 |
| 长期未更新 | -10 | 可能已废弃 |
| 纯套壳无增值 | -10 | 没有独特价值 |

#### 原则 3：证据链完整

每个分数都**可追溯、可验证**。

```yaml
维度: 透明度
得分: 40/100
证据:
  - 类型: about_page
    存在: false
    来源: https://inference.sh/about (404)
  - 类型: team_info
    存在: false
    来源: 官网搜索
  - 类型: contact_info
    存在: false
    来源: 官网搜索
```

#### 原则 4：动态更新

Skill 是活的，评估也要**持续更新**。

- 每次版本更新 → 重新评估
- 发现安全漏洞 → 立即降级
- 社区反馈变化 → 调整得分

---

### 2.4 具体评估维度设计

#### 维度 1：来源可信度 (20%)

**核心问题**：谁开发的？值得信任吗？

| 等级 | 标准 | 得分 |
|------|------|------|
| A | 知名公司/组织（Google、Microsoft、Vercel） | 90-100 |
| B | 有实名团队，有历史项目 | 70-89 |
| C | 个人开发者，资料完整 | 50-69 |
| D | 匿名/信息缺失 | 0-49 |

**采集指标**：
- GitHub 组织/个人资料完整度
- 团队成员公开信息
- 历史项目质量
- 域名注册信息

---

#### 维度 2：透明度 (20%)

**核心问题**：敢不敢公开信息？

| 检查项 | 权重 | 采集方式 |
|--------|------|----------|
| About 页面 | 25% | 爬虫检查 |
| 团队信息 | 25% | 爬虫检查 |
| 联系信息 | 20% | 爬虫检查 |
| README 完整度 | 15% | GitHub API |
| License 声明 | 15% | GitHub API |

**为什么重要**：
- 敢公开信息的，通常更自信、更负责
- 信息不透明的，出问题时找不到人

---

#### 维度 3：可持续性 (15%)

**核心问题**：这个项目能活多久？

| 指标 | 权重 | 标准 |
|------|------|------|
| 最近更新时间 | 40% | <30天: 满分, <90天: 及格, >180天: 0分 |
| 提交频率 | 30% | >10次/月: 满分 |
| Issue 响应时间 | 20% | <7天: 满分 |
| 社区规模 | 10% | Stars > 1000: 满分 |

**为什么重要**：
- 不想用着用着项目死了
- 活跃项目更可能修复 bug

---

#### 维度 4：技术价值 (15%)

**核心问题**：是真技术还是套壳？

| 检查项 | 权重 | 标准 |
|--------|------|------|
| 代码复杂度 | 30% | 非简单转发，有独特逻辑 |
| 测试覆盖率 | 25% | >50%: 满分 |
| 文档完整性 | 25% | API 文档、使用示例 |
| 独特功能 | 20% | 有创新点，非纯 wrapper |

**套壳识别**：
```
纯套壳信号：
- 代码 < 100 行
- 只是转发 API 调用
- 无额外功能
- 价格反而更贵
```

---

#### 维度 5：安全审计 (15%)

**核心问题**：用起来安全吗？

| 检查项 | 权重 | 工具 |
|--------|------|------|
| 依赖漏洞 | 40% | Snyk, npm audit |
| 代码审查 | 30% | 静态分析 |
| 权限要求 | 30% | 人工审查 |

**一票否决**：
- 已知高危漏洞 → 直接 REJECT
- 要求过度权限（如读取 SSH 密钥）→ 直接 REJECT

---

#### 维度 6：社区反馈 (10%)

**核心问题**：真实用户怎么说？

| 来源 | 权重 | 采集方式 |
|------|------|----------|
| GitHub Issues | 40% | API 分析 |
| Reddit/HN 讨论 | 30% | 搜索 + NLP |
| 技术博客 | 20% | 搜索 |
| Twitter 提及 | 10% | API |

**反水军机制**：
- 时间分布分析（突发集中 = 可疑）
- 内容相似度检测
- 账号历史检查

---

#### 维度 7：使用指标 (5%)

**核心问题**：有多少人在用？

| 指标 | 权重 |
|------|------|
| 下载量 | 60% |
| Fork 数 | 20% |
| 被依赖数 | 20% |

**权重最低的原因**：
- 最容易被操纵
- 仅供参考，不作为主要依据

### 2.5 评分算法

```python
def calculate_score(skill):
    # 1. 计算加权基础分
    base_score = sum(
        dimension.score * dimension.weight 
        for dimension in skill.dimensions
    )
    
    # 2. 红旗扣减
    red_flag_penalty = len(skill.red_flags) * 10
    score_after_penalty = max(0, base_score - red_flag_penalty)
    
    # 3. 一票否决检查
    if skill.dimensions.security_audit.score < 30:
        return Score(0, 'REJECT', '存在严重安全风险')
    
    if skill.dimensions.transparency.score < 20:
        return Score(score_after_penalty * 0.5, 'WARNING', '信息极度不透明')
    
    # 4. 确定评级
    if score_after_penalty >= 80:
        return Score(score_after_penalty, 'APPROVE', '评估通过')
    elif score_after_penalty >= 60:
        return Score(score_after_penalty, 'CAUTION', '谨慎使用')
    elif score_after_penalty >= 40:
        return Score(score_after_penalty, 'WARNING', '风险较高')
    else:
        return Score(score_after_penalty, 'REJECT', '不建议使用')
```

### 2.6 公允性保障机制

#### 1. 开源透明
- 所有评估代码开源
- 评分逻辑公开可查
- 接受社区审计

#### 2. 数据可验证
- 每个分数都有数据来源
- 提供原始数据下载
- 支持第三方复核

#### 3. 多方制衡
- 不依赖单一数据源
- 引入社区众包验证
- 建立申诉机制

#### 4. 定期校准
- 每月回顾评估标准
- 根据反馈调整权重
- 公开变更日志

## 四、待解决的问题

1. **数据获取**：GitHub API 限制、网站爬取合法性
2. **主观判断**：某些维度（如"技术价值"）难以完全客观
3. **标准争议**：不同场景下权重是否应该不同？
4. **误伤风险**：严格标准可能错过好项目

---

## 五、下一步

1. **验证这套标准**：用 10-20 个真实 Skill 测试
2. **收集反馈**：让社区参与标准制定
3. **迭代优化**：根据实践调整权重和指标

---

**核心认知**：
> 没有完美的评价标准，但可以有**透明、可验证、持续改进**的标准。

Skill Vetter 的目标不是成为"权威"，而是成为**社区共治的评估基础设施**。
