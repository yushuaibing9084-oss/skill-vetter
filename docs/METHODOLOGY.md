## 评估哲学

### 核心原则

**1. 多维度 > 单一指标**

单一指标容易被针对性操纵。Skill Vetter 使用 7 个维度综合评估，降低操纵可能性。

**2. 透明度 > 完美评分**

我们不追求"权威评分"，而是追求"透明可验证"。每个分数都有明确的来源和证据。

**3. 个性化 > 一刀切**

同样的 Skill，对不同用户价值不同。我们提供匹配度分析，而非绝对好坏判断。

**4. 预期管理 > 功能罗列**

知道一个 Skill"不能做什么"比知道它"能做什么"更重要。

## 七维度评估模型

### 维度权重设计

```
总分 = Σ(维度得分 × 权重)

来源可信度: 20%  ← 最关键
透明度:     20%  ← 最佳风险指标
安全审计:   15%  ← 底线要求
技术价值:   15%  ← 质量指标
可持续性:   15%  ← 长期价值
社区反馈:   10%  ← 参考
使用指标:    5%  ← 仅作参考（最易操纵）
```

### 为什么这样设计权重？

**来源可信度 (20%)**
- 谁做的比做什么更重要
- 知名团队/公司 = 长期维护 + 责任可追溯
- 匿名开发者 = 高风险

**透明度 (20%)**
- 敢公开信息的通常更自信、更负责
- 信息不透明 = 出问题时找不到人
- 最佳风险预测指标

**安全审计 (15%)**
- 底线要求，一票否决
- 已知漏洞 = 直接拒绝
- 过度权限 = 重大风险

**使用指标仅 5%**
- 下载量、Stars 最容易被操纵
- 仅供参考，不作为主要依据

## 各维度详细标准

### 1. 来源可信度 (Source Credibility)

**评估问题**: 谁开发的？值得信任吗？

| 等级 | 标准 | 得分 | 示例 |
|------|------|------|------|
| A+ | 顶级公司/组织 | 95-100 | Anthropic, GitHub, Google |
| A | 知名公司/组织 | 85-94 | Vercel, Microsoft, AWS |
| B+ | 知名开源项目 | 80-84 | Prisma, Next.js |
| B | 有实名团队 | 65-79 | 有公开身份的创业团队 |
| C | 个人开发者 | 45-64 | 有 GitHub 历史的个人 |
| D | 信息不完整 | 20-44 | 资料缺失的开发者 |
| F | 匿名/不明 | 0-19 | 无法确认身份 |

**采集指标**:
- GitHub 组织/个人资料完整度
- 团队成员公开信息
- 历史项目质量
- 域名注册信息

---

### 2. 透明度 (Transparency)

**评估问题**: 敢不敢公开信息？

| 检查项 | 权重 | 标准 |
|--------|------|------|
| About 页面 | 25% | 有 = 25分, 无 = 0分 |
| Team 信息 | 25% | 有 = 25分, 无 = 0分 |
| Contact | 20% | 有 = 20分, 无 = 0分 |
| License | 15% | 明确 = 15分, 模糊 = 5分 |
| README | 15% | 完整 = 15分, 极简 = 5分 |

**为什么透明度重要**:
- 敢公开 = 更自信、更负责
- 不公开 = 可能有问题要隐藏
- 是预测风险的最佳单一指标

---

### 3. 安全审计 (Security Audit)

**评估问题**: 用起来安全吗？

| 检查项 | 权重 | 标准 |
|--------|------|------|
| 依赖漏洞 | 40% | npm audit / Snyk 扫描 |
| 代码审查 | 30% | 静态分析 + 人工抽查 |
| 权限要求 | 30% | 是否要求过度权限 |

**一票否决项**:
- 已知高危漏洞 → 直接 REJECT
- 要求读取 SSH 密钥、密码等敏感数据 → 直接 REJECT
- 代码混淆/加密 → 严重扣分

---

### 4. 技术价值 (Technical Value)

**评估问题**: 是真技术还是套壳？

| 检查项 | 权重 | 标准 |
|--------|------|------|
| 代码复杂度 | 30% | 非简单转发，有独特逻辑 |
| 测试覆盖率 | 25% | >50% = 满分 |
| 文档完整性 | 25% | API 文档、使用示例 |
| 独特功能 | 20% | 有创新点，非纯 wrapper |

**套壳识别信号**:
```
纯套壳指标:
- 代码 < 100 行
- 只是转发 API 调用
- 无额外功能
- 价格反而更贵
```

---

### 5. 可持续性 (Sustainability)

**评估问题**: 这个项目能活多久？

| 指标 | 权重 | 标准 |
|------|------|------|
| 最近更新时间 | 40% | <30天=满分, <90天=及格, >180天=0分 |
| 提交频率 | 30% | >10次/月=满分 |
| Issue 响应 | 20% | <7天=满分 |
| 社区规模 | 10% | Stars > 1000=满分 |

---

### 6. 社区反馈 (Community Feedback)

**评估问题**: 真实用户怎么说？

| 来源 | 权重 | 采集方式 |
|------|------|----------|
| GitHub Issues | 40% | API 分析 |
| Reddit/HN 讨论 | 30% | 搜索 + NLP |
| 技术博客 | 20% | 搜索 |
| Twitter 提及 | 10% | API |

**反水军机制**:
- 时间分布分析（突发集中 = 可疑）
- 内容相似度检测
- 账号历史检查

---

### 7. 使用指标 (Usage Metrics)

**评估问题**: 有多少人在用？

| 指标 | 权重 |
|------|------|
| 下载量 | 60% |
| Fork 数 | 20% |
| 被依赖数 | 20% |

**权重最低的原因**:
- 最容易被操纵（CI/CD 刷量、买 Stars）
- 仅供参考，不作为主要依据

## 红旗机制

### 什么是红旗？

红旗是**严重风险信号**，直接降低评级，不管其他维度得分多高。

### 红旗列表

| 红旗 | 扣分 | 说明 |
|------|------|------|
| 官网无团队信息 | -10 | 不敢公开身份 |
| 无融资/商业模式 | -10 | 可持续性存疑 |
| 已知安全漏洞 | -20 | 底线问题 |
| 过度权限要求 | -15 | 可能窃取数据 |
| 长期未更新 (>180天) | -10 | 可能已废弃 |
| 纯套壳无增值 | -10 | 没有独特价值 |
| 代码未开源 | -15 | 无法审计 |
| 开发者身份不明 | -15 | 无法追责 |

### 一票否决

某些红旗直接导致 REJECT：
- 透明度 < 20 分
- 安全审计 < 30 分
- 4 个以上红旗

## 评分算法

```javascript
function calculateScore(skill) {
  // 1. 计算加权基础分
  let baseScore = 0;
  for (const [key, dim] of Object.entries(skill.dimensions)) {
    baseScore += dim.score * WEIGHTS[key];
  }
  
  // 2. 红旗扣减
  const redFlagPenalty = skill.red_flags.length * 10;
  let scoreAfterPenalty = Math.max(0, baseScore - redFlagPenalty);
  
  // 3. 一票否决检查
  if (skill.dimensions.security_audit.score < 30) {
    return { score: 0, rating: 'REJECT', reason: '存在严重安全风险' };
  }
  
  if (skill.dimensions.transparency.score < 20) {
    return { 
      score: scoreAfterPenalty * 0.5, 
      rating: 'REJECT', 
      reason: '信息极度不透明' 
    };
  }
  
  // 4. 确定评级
  if (scoreAfterPenalty >= 80) {
    return { score: scoreAfterPenalty, rating: 'APPROVE' };
  } else if (scoreAfterPenalty >= 60) {
    return { score: scoreAfterPenalty, rating: 'CAUTION' };
  } else if (scoreAfterPenalty >= 40) {
    return { score: scoreAfterPenalty, rating: 'WARNING' };
  } else {
    return { score: scoreAfterPenalty, rating: 'REJECT' };
  }
}
```

### 评级标准

| 总分 | 评级 | 建议 |
|------|------|------|
| 80-100 | ✅ APPROVE | 放心使用 |
| 60-79 | ⚠️ CAUTION | 谨慎使用，阅读风险说明 |
| 40-59 | ❌ WARNING | 风险较高，寻找替代方案 |
| 0-39 | 🚫 REJECT | 不建议安装，存在严重风险 |

|------|-----------|------|--------------|------------------|
| 安全漏洞检测 | ✅ | ✅ | ❌ | ✅ |
| 来源可信度评估 | ❌ | ❌ | ❌ | ✅ |
| 透明度评估 | ❌ | ❌ | ❌ | ✅ |
| 可持续性预测 | ❌ | ❌ | ❌ | ✅ |

### 关键差异

**vs npm audit**:
- npm audit 只关注依赖漏洞
- Skill Vetter 关注整体质量和风险

**vs Snyk**:
- Snyk 是商业工具，评估逻辑黑盒
- Skill Vetter 完全开源，逻辑透明

**vs GitHub Stars**:
- Stars 容易被操纵
- Skill Vetter 多维度 + 红旗机制，更难操纵

## 局限性与改进方向

### 当前局限性

**1. 数据获取限制**
- GitHub API 有速率限制
- 某些网站不允许爬取
- 部分数据需要人工验证

**2. 主观判断不可避免**
- "技术价值"难以完全客观
- "社区反馈"的 NLP 分析有误差
- 权重设计存在主观性

**3. 可能误伤**
- 严格标准可能错过好项目
- 新项目的可持续性难以评估

### 改进方向

**短期**:
- [ ] 众包验证：让社区参与评估
- [ ] 反馈闭环：使用后反馈改进算法
- [ ] 更多数据源：接入更多平台

**中期**:
- [ ] 动态权重：根据场景调整权重
- [ ] 预测模型：用 ML 预测可持续性
- [ ] 行业标准：建立 Skill 评估标准

**长期**:
- [ ] 去中心化：区块链存证评估历史
- [ ] 实时更新：监控 Skill 变化自动更新评分
- [ ] 生态整合：与平台深度集成

## 总结

Skill Vetter 的评估方法论核心：

1. **多维度综合评估** — 降低单一指标操纵风险
2. **红旗机制** — 一票否决严重风险
3. **透明可验证** — 每个分数都有来源
4. **持续改进** — 根据反馈优化算法

我们的目标不是成为"权威"，而是成为**社区共治的评估基础设施**。
